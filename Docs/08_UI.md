# ONE BRAHAM — interface

The HUD, the menus and the settings. What each element is for, why it looks the
way it does, and the exact numbers.

**Interface brief in one line:** it should look like a building's signage
system — restrained, legible, slightly institutional — and it should disappear
the moment a player does not need it. Nothing in this game pulses, bounces,
rotates or sparkles.

---

## 1. Why the HUD is built in C++

`UOneBrahamHUDWidget` builds its entire layout from code when its widget tree has
no root. This is deliberate and it has three consequences that matter:

1. **The game is playable before any UMG asset exists.** A fresh clone with no
   content has a working HUD, crosshair, compass, health, ammo and extraction
   timer.
2. **The layout cannot be broken by a designer's edit.** The critical path is not
   living in an asset that can be replaced with a wrong one.
3. **A designer can take over one element at a time.** Adding a widget to
   `WBP_OneBrahamHUD` overrides that element; everything else keeps coming from
   code. This is how UI work should degrade.

`WBP_OneBrahamHUD` is the override path.

### `DT_HUDStrings`

`FOneBrahamHUDStringRow` (UI/OneBrahamHUDStringTable.h) is the row struct and
`DT_HUDStrings` is the table: **31 rows**, every string the HUD shows, so the copy
can be localised and reviewed by a writer without opening a widget. The rows are
compiled in as well (`OneBrahamHUDStrings::All()`), which is the same rule as the
layout above: a fresh clone with no content has the words as well as the panels,
and `build_ui.py` writes the asset from that list.

This table is the one place a HUD string lives. It once was not: `build_ui.py`
created an empty `DataTable` with a `struct` property set to a row struct that did
not exist, wrote no rows, and nothing in C++ read it; the claim above was a
sentence in a document.

**Which layer shows which key.** Fourteen keys are referenced from C++ —
`HUD_Downed_BleedOut`, `HUD_Downed_CallHelp`, `HUD_Extraction_Hold`,
`HUD_Extraction_Contested`, `HUD_Extraction_Failed`, `HUD_Floor_Format`,
`HUD_Match_Extracted`, `HUD_Objective_Lockdown`, `HUD_Objective_Purge`,
`HUD_Objective_Winch`, `HUD_Squad_Downed`, `HUD_Voice_Proximity`,
`HUD_Voice_Squad`, `HUD_Voice_Team`. The other seventeen are shown by the
Blueprint layer, because that is what owns them:

| Key | Shown by |
| --- | --- |
| `HUD_Mode_Ascent`, `HUD_Mode_FireDrill`, `HUD_Mode_NightShift` | the loading screen and the mode card, drawn from the match settings asset the mode was picked from |
| `HUD_Objective_SignIn`, `HUD_Objective_Ascend`, `HUD_Objective_Hold` | the objective line on `WBP_OneBrahamHUD`, which the map sets from the phase |
| `HUD_Prompt_Override`, `HUD_Prompt_Card`, `HUD_Prompt_Revive`, `HUD_Prompt_Execute`, `HUD_Prompt_Breach` | interactables whose prompt is authored in Blueprint. The C++ access targets build their own prompt instead, because theirs names the destination: "Hold E - Executive Suite" |
| `HUD_Locked_Executive`, `HUD_Locked_Secure`, `HUD_Locked_Skydeck` | the badge-required line on the door widgets |
| `HUD_Match_NoSurvivors` | the end-of-match screen |
| `HUD_Squad_You`, `HUD_Squad_Dead` | the squad panel's status words |

`check_hud_strings.py` keeps that honest: every key must exist, and every key must
be either referenced from C++ or listed in the table above, so no row is in the
table without something that shows it.

One element does not come from the HUD's own data flow, and it is worth naming:
the **death screen**. It is pushed by
`AOneBrahamPlayerController::ClientShowDeathScreen`, a Client RPC, because a
death is detected on the server and the player who died is on another machine.
Its cause line is built once, from the kill-feed entry, in
`AOneBrahamCharacter::BuildDeathCauseText`, so the feed and the screen cannot
disagree about who killed whom.

## 2. Palette and type

### Colour

| Name | RGB (0–1) | Where |
| --- | --- | --- |
| Primary blue | 0.000, 0.439, 0.753 | friendly UI, objective, own team |
| Deep navy | 0.016, 0.063, 0.145 | panel backgrounds (0.86 alpha) |
| Signal blue | 0.078, 0.522, 1.000 | pings, interaction prompts, extraction |
| Safety yellow | 1.000, 0.804, 0.000 | warnings, low ammo, lockdown |
| Emergency red | 0.867, 0.118, 0.122 | critical health, damage direction, purge |
| Light grey | 0.878, 0.898, 0.922 | body text |
| White | 1.000, 1.000, 1.000 | emphasis only |

These seven come from `Config/DefaultGame.ini` `[OneBrahamGameSettings]`, and
`OneBrahamUIStyle.cpp` reads them from there. `build_ui.py` verifies the two
agree on every run, so the ini and the code cannot drift.

### Type scale

| Token | Size (px at 1080p) | Weight | Use |
| --- | --- | --- | --- |
| Micro | 10 | Regular | timestamps, key hints |
| Small | 12 | Medium | labels, captions, squad list |
| Body | 14 | Regular | subtitles, descriptions |
| Medium | 18 | Medium | ammo count, objective line |
| Large | 28 | Bold | health, hold timer |
| Huge | 44 | Bold | extraction countdown |
| Title | 64 | Black | mode name on the loading screen |

Tabular figures are required for ammo, health, the timer and the scoreboard. A
number that jitters when it changes is a number a player cannot read at a glance.

### Spacing and shape

Spacing scale: 2, 4, 6, 8, 12, 18, 24, 32 px. Corner radius: panels 4 px,
buttons 2 px, pill 8 px. Panel treatment: one flat fill at navy 0.86 alpha, a
1 px light-grey 0.18 border, and no drop shadow. Anything else reads as a game
UI, and this game's UI is supposed to read as part of the building.

### The three overlays

Three elements are not part of the HUD: they are the HUD the player asks for, and
they are bound to three Enhanced Input actions that used to be generated by the
content pipeline with no handler at all, and no field in `DA_InputConfig` to
point at them.

| Overlay | Action | Input | What it is |
| --- | --- | --- | --- |
| HUD toggle | `IA_ToggleHUD` | `F1` | Hides the whole interface. Session-only: the saved settings are a scale and a set of element switches, not "hide everything". The widget is hidden, not destroyed, because this key gets pressed to take screenshots and rebuilding a HUD drops frames exactly then. |
| Floor plan | `IA_Map` | `M` (tap) | Eighteen floors, sealed floors, the squad, the extraction. Left edge, vertically centred, so it sits beside the player's field of view rather than on the crosshair. |
| Comms wheel | `IA_VoiceLineMenu` | `X`, press-aim-release | Eight lines, chosen by mouse direction, click, or a number key. |

**The floor plan is not a minimap.** One Braham has no minimap anywhere, on
purpose: a minimap flattens a fifteen-floor building into a corridor and removes
the thing the game is about, which is knowing the tower. The plan answers *which
floor*; it never answers *where in the room*, and it does not know where the enemy
is. What it shows, in the order the eye should find it:

1. the floor the player is on, as a filled bar;
2. a downed squadmate's floor, in alarm red, pulsing at 0.5 Hz — the only element
   on the panel that should change what a player does;
3. floors sealed by the lockdown, muted red;
4. squadmates per floor, in signal blue;
5. the extraction, in safety yellow, with the hold progress, because thirty
   seconds is exactly long enough to run for.

Nothing on it is drawn by a Blueprint: `UOneBrahamFloorPlanWidget` paints the
whole panel in `NativePaint`, which is what makes it crisp at 4K, identical on
every machine, and screenshot-testable in a headless test. `WBP_FloorPlan` exists
so a designer can put anything they like *around* it.

**Nothing in the HUD ticks.** A C++ `UUserWidget` is created with
`EWidgetTickFrequency::Auto`, and Auto means *tick only if this widget has a tick
event implemented in Blueprint* — an override of `NativeTick` is not one, so the
engine never calls it. Three widgets here animated in a `NativeTick` that would
never have run, including the HUD's banner, subtitle and damage-flash timers: they
would have frozen at whatever the first frame left them at, silently, with no
warning and nothing in a screenshot to give it away.

Time-based UI therefore reads the clock in `NativePaint` — the one callback a
visible widget is guaranteed every frame — and derives its state from the world
time it was opened (`UOneBrahamFloorPlanWidget`, `UOneBrahamQuickLineWidget`) or
from the elapsed time since the last paint (`UOneBrahamHUDWidget`). It costs
nothing, it is exactly as smooth as the framerate, and it cannot be switched off
by a property nobody remembered. `check_uht_contracts.py` fails the build on a
widget that overrides `NativeTick` without deliberately asking for a tick by
assigning `TickFrequency`.


Its data comes from `UOneBrahamBuildingLayoutAsset`, and the compiled-in default
of that asset is the shipping building — the same eighteen floors and nine areas
the content build lays out. `Docs/09_Map_Implementation.md` §2 covers the asset;
`check_building_layout.py` fails the build if the two tables disagree.

**The comms wheel is not a menu.** Eight segments, and the number is a design
decision rather than a limit: a wheel with twenty entries cannot be hit without
looking, and looking away in a firefight is how players die. The ordering is
clockwise from the top, most urgent first:

| # | Segment | Line id | Says |
| --- | --- | --- | --- |
| 1 | CONTACT | `V_CONTACT_ENEMY` | "Contact. One." |
| 2 | PUSH | `V_PUSH_NOW` | "Now. Go now." |
| 3 | HOLD | `V_HOLD_POSITION` | "Hold here. Let them come to us." |
| 4 | RELOADING | `V_RELOADING` | "Reloading - cover me." |
| 5 | MOVING UP | `V_PING_MOVE` | "Move up." |
| 6 | MAN DOWN | `V_MAN_DOWN` | "Somebody's down - nearest one, get to him." |
| 7 | QUIET | `V_QUIET` | "Quiet - I heard something in the ceiling." |
| 8 | NEGATIVE | `V_ACK_NEGATIVE` | "No. Not that way." |

Every segment speaks a line that is already in the script, with the delivery
notes, archetype filters and cooldowns somebody has already thought about. The
first draft of this table named eight plausible-sounding ids, seven of which did
not exist anywhere in the game: a wheel where seven of eight segments do nothing
and every screenshot looks correct. `V_MAN_DOWN` is the one line the wheel did
need and the script did not have, because the downed player cannot say it.
`Docs/14_Voice_Script.md` §3 is the recording brief for all eight, and
`check_voice_lines.py` fails the build if a segment names a line that is not
there.

Interaction model: **press, aim, release.** A quick tap-release inside the dead
zone (68 px) says nothing, deliberately — an accidental "enemy spotted" is worse
than an unspoken one. A greyed segment is a line on cooldown, with the remaining
seconds drawn on it, so the player is told before they commit rather than after.
Escape or a click in the dead zone cancels.

Nothing is spoken on the client. Selecting a segment calls
`AOneBrahamPlayerController::RequestQuickLine`, which asks the server; the server
resolves the line against the voice script, the archetype filter and the
cooldowns, and multicasts it. A modified client can only ask faster — the answer
is still the server's.

### The three rules the HUD follows

1. **Nothing is always on unless it is always relevant.** The extraction timer
   appears when an extraction exists; the lockdown indicator appears when the
   building starts locking down. A HUD that shows everything is a HUD nobody
   reads.
2. **Every element is legible on a grey wall and on a black stairwell.** All text
   has a 1 px dark outline and a 40% black backing; the crosshair has a 1 px
   outline in both colours.
3. **The player's own state is never ambiguous.** Health, ammo and bleed-out are
   readable in one glance from the corner of an eye, at 1080p, on a TV at 3 m,
   and with the HUD at 80% scale (a settings option that exists because some
   players need it).

### 3.x The induction and the death recap

**The induction.** A player whose profile has never finished it gets a guided
run of the ground floor (`UOneBrahamInductionComponent`, logic in
`Core/OneBrahamInduction.h`): one prompt at a time on the HUD's sub-banner -
walk in, look round, sprint, crouch, find a staff keycard at reception, badge
through the gates, ride the escalators, fire, reload. Each step ends the moment
the player does it; a step with no progress moves on after 45 seconds. When it
ends the profile's `bHasSeenTutorial` is set and saved.

**The death recap.** Under the death screen's cause line, one line per attacker
in the last twelve seconds, most damaging first - hits, damage, where they
landed, from how far - then what the killer had left
(`Core/OneBrahamDeathRecap.h`). It stands in for a replay killcam.

**The microphone meter.** Settings > Voice shows the input level on a
-60..0 dB scale with a peak hold, and a tick where the voice-activation gate
opens; the bar takes the accent colour once it crosses the tick.

## 4. Menus

### The widget assets

Eleven blueprints, created by `build_ui.py`. Three are loaded by C++ by full path
and seven are opened by the menu stack in `L_MainMenu`, which is authored content:
a CommonUI activation stack with `WBP_MainMenu` at the root, routing to the other
six. Nothing in C++ loads those seven, and that is deliberate — a menu is layout
and animation, which is what a designer is for.

| Asset | Parent | Opened by | Contents |
| --- | --- | --- | --- |
| `WBP_OneBrahamHUD` | `UOneBrahamHUDWidget` | `UOneBrahamHUDComponent`, by path | The in-match HUD. Empty by default: the C++ widget draws the layout |
| `WBP_OneBrahamScoreboard` | `UOneBrahamHUDWidget` | nothing at present | Reserved for a restyled scoreboard. Not loaded: it is parented to the HUD class, and the scoreboard is `UOneBrahamScoreboardWidget` (section 4.1). Reparenting it to that class is the override path |
| `WBP_FloorPlan` | `UOneBrahamFloorPlanWidget` | `UOneBrahamHUDComponent`, by path | The floor plan. The C++ parent draws it; the Blueprint adds the frame |
| `WBP_QuickLineWheel` | `UOneBrahamQuickLineWidget` | `UOneBrahamHUDComponent`, by path | The comms wheel. The C++ parent owns the ring, labels and cooldowns |
| `WBP_MainMenu` | `UUserWidget` | the `L_MainMenu` menu stack (root) | PLAY, WARDROBE, SETTINGS, SERVER BROWSER, QUIT. Steam overlay aware |
| `WBP_DeployScreen` | `UUserWidget` | `WBP_MainMenu` → PLAY | Archetype carousel, loadout, squad ready state, spawn preview |
| `WBP_Wardrobe` | `UUserWidget` | `WBP_MainMenu` → WARDROBE | Twelve cosmetic slots, unlocks, no stat text anywhere |

| `WBP_ServerBrowser` | `UUserWidget` | `WBP_MainMenu` → SERVER BROWSER | Steam server list, favourites, ping, mode filter |

`check_hud_strings.py` enforces the two halves of that table: every widget the

### 4.1 The in-match menus: scoreboard, pause menu, settings

Three screens are built in C++ by the same rule as the HUD (section 1): a clean
checkout can mute a colleague, change its field of view and leave the match
before any widget asset exists. All three derive from `UOneBrahamMenuWidget`
(`UI/OneBrahamMenuWidget.h`), which holds the construction helpers - the
signage button, slider, checkbox, combo box, hairline rule and fixed-width cell -
so the three cannot drift apart in style.

**They are not panels of the HUD.** `UOneBrahamHUDWidget` is hit-test invisible on
purpose (it must never take a click from the player), so a button inside it can
be seen and never pressed. `UOneBrahamHUDComponent` creates
`UOneBrahamScoreboardWidget` (viewport layer 20) and `UOneBrahamPauseMenuWidget`
(layer 30) on first use, above the HUD (0) and the two overlays (1, 2). The HUD's
`Panel_Scoreboard` and `Panel_PauseMenu` survive only as optional bindings.

**The look.** Building signage: navy panels, light-grey type, hairline rules and
one accent - signal blue - for the thing that is yours or the thing that has
focus. Each panel carries a 4 px accent bar down its left edge, as a floor
directory does. No other colour appears; a state that needs emphasis gets weight
or opacity, not a new hue.

| Screen | Opens | Closes | Input mode while open |
| --- | --- | --- | --- |
| Scoreboard | hold `IA_Scoreboard` (Tab / View) | release | game and UI, cursor on, focus left on the viewport |
| Pause menu | `IA_PauseMenu` (Escape / Start) | RESUME, Escape, B or Start (one step back at a time) | UI only, cursor on, focus on the menu |
| Settings | SETTINGS in the pause menu | BACK, Escape or B; applies and saves first | as the pause menu |

`AOneBrahamPlayerController::RefreshMenuInputMode` sets those modes, in one place
because the two menus interact. The scoreboard keeps the game's input: the player
still moves, and the Tab release has to reach Enhanced Input to close the board -
which is why its mute buttons are not focusable (a focused button would swallow
the release). The pause menu takes the game's input away entirely, so nothing
fires, reloads or walks while a player is in Settings; the menu handles its own
back key, so Escape still works. Opening the pause menu closes the scoreboard
(its Tab release would never arrive) and flushes held keys. Only a standalone
game actually pauses: a networked match belongs to the server.

#### Scoreboard

The lobby's directory board. A header with the server, the head count, the mode,
the phase and the clock (remaining in a timed mode, elapsed in ASCENT), and in
FIRE DRILL the score between the teams. Then one block per squad (ASCENT, NIGHT
SHIFT) or team (FIRE DRILL), the local player's block first; inside a block, by
objective score, then kills, then fewest deaths. Columns:

| Column | Source | Notes |
| --- | --- | --- |
| lamp | `bIsTransmitting` (and `IsLocalTransmitting` for your own row) | accent while transmitting; dark for a player you have muted |
| NAME | `GetPlayerName` | the local row is tinted and its name set in the accent |
| ROLE | `ArchetypeTag` leaf, in signage case | "BUSINESS ANALYST", "IT OPERATIONS" |
| STATUS | `LifeState` | ON SITE, DOWNED (bold white - the one state that changes what a colleague does next), SIGNED OUT, EXTRACTED; signed-out rows fade |
| K / D / A / OBJ | `Kills`, `Deaths`, `Assists`, `ObjectiveScore` | right-aligned, ledger style |
| PING | `GetPingInMilliseconds` | "BOT" for bots |
| VOICE | `UOneBrahamVoiceSubsystem::SetPlayerMuted` / `IsPlayerMuted` | MUTE / MUTED; not shown on your own row or a bot's |

It refreshes four times a second while open, from the core ticker (`FTSTicker`):
that runs while the game is paused and is unhooked when the board closes. Rows
are updated in place and rebuilt only when the roster or its order changes, so a
mute button is not replaced under the cursor. The board never stores mute state;
it asks the voice subsystem on every refresh.

#### Pause menu

RESUME, SETTINGS, then - after a rule, so the hand that reaches for RESUME does
not land on them - LEAVE MATCH and QUIT TO DESKTOP. Both exits ask first, with
the safe answer (STAY) focused, because a second press of the confirm key is the
usual way to leave a match by accident. LEAVE MATCH calls
`UOneBrahamGameInstance::TravelToMainMenu`; QUIT calls `QuitGame`. A
`PauseMenuWidgetClass` set on the controller Blueprint still replaces the C++
menu wholesale.

#### Settings

`UOneBrahamSettingsWidget`, five tabs. Every control writes into
`UOneBrahamGameUserSettings` - through the settings' own setter where one exists,
into the field where it does not (`SetFOV` and the sensitivity setters save the
file on every call, which a dragged slider would do thirty times a second).
Volumes and voice gains are heard as they move; everything else waits for
`ApplySettings`, which runs with `SaveSettings` on APPLY and on BACK. Leaving the
screen never discards a change.

| Tab | Settings |
| --- | --- |
| GRAPHICS | quality preset (Low - Ultra), resolution scale 50-100 %, field of view 70-110°, motion blur, film grain, chromatic aberration, depth of field, camera shake 0-100 % (0 turns it off) |
| AUDIO | master, music, building ambience, effects, weapons, footsteps, dialogue, announcements, interface, voice chat; building announcements on/off |
| VOICE | transmit mode (push to talk, voice activation, open microphone, off), microphone gain and incoming gain 0-200 %, noise gate threshold; the macOS microphone permission in words (`OneBrahamMicrophonePermission::GetStatus`, then `IsMicrophonePermissionDenied` / `HasWorkingMicrophone`), the capture device, and a transmit lamp |
| GAMEPLAY | mouse sensitivity, aiming sensitivity, invert; controller sensitivity, invert; hold to sprint, toggle crouch, toggle aim; view bobbing, reduce motion; subtitles, blood (`SetGoreEnabled`) |
| CONTROLS | read-only: every action in the default and common mapping contexts, keyboard-and-mouse and controller keys in two columns |

The transmit lamp stands in for a level meter: the voice component exposes
whether voice is leaving the machine (`IsLocalTransmitting`) but not an input
level. In voice activation that is the gate, which is what a player tuning the
threshold needs to see. A live meter needs a level getter on
`UOneBrahamProximityVoiceComponent`.

Keyboard and gamepad: every button, slider, checkbox and combo is focusable and
Slate's own navigation moves between them; the focused button is drawn exactly as
a hovered one (restyled from `NativePaint`, because `UButton` has no focused
brush); the shoulder buttons change tab; the settings pages scroll to follow
focus.

### The deploy screen is the most important screen

It is where a player makes three decisions in thirty seconds — who they are, what
they carry, where they go — and the design goal is that those three decisions
should each be obvious and interesting. The archetype is cosmetic; the loadout is
not; the spawn preview shows the first 20 m of the map.

### Settings that must exist

| Group | Settings |
| --- | --- |
| Video | resolution, display mode, quality preset 0–4, resolution scale, FOV 60–110, motion blur 0–100%, DOF, film grain, chromatic aberration, V-Sync, frame cap |
| Audio | master, music, ambience, SFX, weapons, footsteps, dialogue, announcements, UI, voice; a mono mix; dynamic range (night mode / cinema) |
| Controls | every action rebindable, per-device, with conflict detection; sensitivity, ADS multiplier, inverse Y, hold-or-toggle for sprint, crouch and aim |
| Gameplay | HUD scale 80–120%, crosshair style and colour, damage numbers, hit markers, subtitles with size and background, ping wheel, objective markers |
| Accessibility | subtitles on by default, colour-blind modes for the four palettes used in the game, high-contrast prompts, hold-to-press durations (0.5× / 1× / 2×), screen shake intensity 0–100%, audio visualisation for the alarm and the extraction beacon |

Colour-blind modes are not a filter slapped over the frame: the four palettes
(gameplay markers, foliage-free environments, the purge lighting, and the alarm
beacons) each have their own alternative values, because a filter that turns the
whole game orange is a filter that makes the game worse.

## 5. CommonUI

CommonUI is used for the menu stack (activation stacks, back handling, input
routing), because a PC game with a controller needs focus management that works
and rolling that yourself is three weeks for a worse result. The in-match HUD
does not use CommonUI at all: it is a single always-on widget and the extra
layer of routing would cost frame time for nothing.

## 6. Building the UI content

```
Scripts\BuildContent.bat --only ui
```

creates 11 widget blueprints, the HUD string table (31 strings) and the font slot, and
verifies the palette. The three that matter most to a reader of this document are
`WBP_OneBrahamHUD`, `WBP_FloorPlan` and `WBP_QuickLineWheel` — the last two are
thin subclasses, because their C++ parents draw themselves and the Blueprint is
only where a designer restyles them. The font is imported by
`Scripts\Import_Font.bat`; the composite font's weights and sizes are the table in
section 2.

There used to be a twelfth: `WBP_VoiceWheel`, a stub the builder created so that
references to it would not break. No reference existed — not in the code, not in
a menu, not in a Blueprint, since the whole content directory is generated — and
the only file that mentioned it was this one. It was a widget whose documentation
was its reason to exist, so both are gone.
