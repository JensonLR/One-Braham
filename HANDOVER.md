**Three things have never happened, and nothing in this repository pretends
otherwise.** They are the first three items of work for whoever picks this up.

1. **No line of this C++ has been compiled.** There has been no Unreal Engine
   install anywhere in this project's history. The checkers in
   `Tools/Python/onebraham/` are stand-ins for the parts of a compiler that can be
   emulated textually: declared-but-undefined members, call arity, UnrealHeaderTool
   contracts, scoped enums used with relational operators, members that shadow
   engine properties. They are good at those five things and blind to everything
   else. Expect compile errors on the first `Build`. They are the work, not a
   setback.
2. **No asset has been built.** The pipeline that builds them (`build_materials.py`,
   `build_environment.py`, `build_weapons.py`, `build_characters.py`, `build_vfx.py`,
   `build_ui.py`, `build_audio.py`, `build_props.py`, `build_input.py`) has never
   run, because it runs inside the editor.
3. **No test has been run.** `Scripts/RunTests.bat` needs the editor, and the
   suite's own design notes in `Docs/18` §2.2 say which categories are covered by
   what until the level exists.

## 2. Verify before you trust

Every command below is engine-free. Run all of them from the repository root, and
set the import root once per shell - every checker is a module and imports the
package the pipeline shares:

```
export PYTHONPATH=Tools/Python
```

If the shell's locale is ASCII - this sandbox's is - also `export PYTHONUTF8=1`. The
tools print and read UTF-8, and under an ASCII locale a single raised exception
fails inside the traceback renderer instead of showing you the error:
`report_uncalled.py` reports its 83 findings happily and then dies with a
`UnicodeDecodeError` from `linecache` if anything goes wrong after that.

`run_all.py` sets it for the steps it runs, so it works either way; nothing else
does.

| Command | Expected | What it proves |
| --- | --- | --- |
| `python3 Tools/Python/onebraham/run_all.py --text-only` | `BUILD OK: 18 step(s) succeeded` | every textual check in the project, in the order they must run |
| `python3 Tools/Python/onebraham/validate_project.py` | `32 pass, 2 warn, 0 fail` | the two warnings are the fresh-clone manifest and surface coverage; anything else is a regression |
| `python3 Tools/Python/onebraham/check_doc_numbers.py` | `89 numbers checked. agree. OK` | every count quoted in `Docs/17` and the README against the count the tooling produces |
| `python3 Tools/Python/onebraham/check_interaction.py` | `checks: 281` | the interaction surface: classes, tables, tags, montage chain, interface conformance |
| `python3 Tools/Python/onebraham/check_cpp_symbols.py` | `855 declarations`, `2096 hygiene checks`, `OK` | declared-but-undefined members, scoped enums, shadowed engine properties, duplicate definitions, float literals, unbudgeted Server RPCs |
| `python3 Tools/Python/onebraham/report_uncalled.py` | `48 member(s) with no call site` | the triage list in §4.2. **This is a report, not a gate** |

Each checker also runs standalone with the import root, which is the only thing
that ever trips anyone up:

```
cd /home/user/One-Braham
PYTHONPATH=Tools/Python python3 Tools/Python/onebraham/check_interaction.py
```

Reports land in `Saved/Build/`, `Saved/Validation/` and `Saved/Benchmarks/` (none
of it committed). When a checker fails, read its own output — never guess a count.
`check_doc_numbers.py` names the offending row and the number the tooling produced.

## 3. What is verified, and what that means

Verified: the module's declarations and definitions agree; every UHT contract
(that `UFUNCTION`/`UPROPERTY` specifiers describe) is satisfied; call sites cannot
have impossible arity; every documented number matches the code or the pipeline;
every gameplay tag the code asks for is declared; every interaction class
implements the interface correctly; the audio bank, HUD string table, cosmetic
wardrobe, weapon armoury and voice line set agree with their docs.

Not verified, and by design: anything that needs an engine. Runtime behaviour,
replication, Blueprint assets, materials, Niagara, animation, sound, network
transport, Steam, and the honest question of whether the game is *fun*.

The four bugs this project found in code that had been reviewed three times were
all found by a *new* rule, and every rule was then sabotaged on purpose to prove it
fires (the sabotage scripts are described in the commit messages; the pattern is in
`/tmp/obs/` in any session that wrote one, and the rules are listed in the header
of each checker). If you add a rule, sabotage it before you trust it.

## 4. What is left

### 4.1 Make it compile

Open `OneBraham.uproject` in UE 5.5, generate project files, build the Editor
target. Fix what the compiler says, in order, in bulk where the error repeats.
Every fix is a commit, and `check_cpp_symbols.py` plus `check_uht_contracts.py`
run after each one. Expect the first pass to be large; expect the second to be
small; expect the first *run* (not compile) to be a different list again.

### 4.2 The uncalled-API triage — 48 members

`Tools/Python/onebraham/report_uncalled.py` lists every member function that is
declared, defined and never called anywhere in the module. It was 83 at the
first handover; it is 48 now, and the group still matters more than the count.

**Not Blueprint: none that are real.** The audio cue wrappers, the gamepad look,
the extraction abort and the rest of the old Group A have been wired or deleted.
The report still shows `SOneBrahamLoadingScreen::Construct`, which Slate calls
through `SNew` (a false positive of a text search).

**Blueprint (`[BP]`): 48.** They are `BlueprintCallable` and no C++ calls them,
which is correct only if a Blueprint does. The front end no longer depends on
any of them: the main menu, settings, rebinding, results and loading screens are
C++ (`Docs/08` §4). What remains is mostly read-only queries a designer's
Blueprint will want (`IsOnPad`, `GetPaneHealth01`, `IsCosmeticUnlocked`) plus a few deliberate designer hooks (`ServerLock`,
`ServerSlamClosed`, `AddArmour`, `SetPendingMatchSettingsOverride`). Treat the
list as a contract. Delete a member a release proves nobody needed, rather than
leaving a third state.

### 4.3 Build the content

`Scripts/BuildContent.bat` runs the nine builders in their required order and
writes `Tools/Python/onebraham_build_manifest.json`. This is where the game becomes
visible: the fifteen floors, the eight areas, the armoury, the wardrobe, the HUD,
the Niagara systems, the audio bank and the map. Every builder reports created,
updated, skipped and failed assets; `validate_project.py`'s two warnings clear once
the manifest exists. Fix the builders the way you fix C++: one change, one run,
read the report.

### 4.4 Make it look, sound and move like the documents say

`Docs/10` (materials, lighting, dressing), `Docs/11` (Niagara, with parameters and
budgets), `Docs/12` (audio classes, mixes, the recording brief), `Docs/13` (six
archetypes, clothing, cosmetics), `Docs/14` (171 voice lines, every one different, with per-line
direction), `Docs/15` (briefs for everything a person must make), `Docs/16`
(marketplace fallbacks with licences). Anything an editor has to be told is in
those documents as instructions, not as wishes — a node graph is a numbered list of
nodes and settings, a Niagara system is a module table, an animation is a
specification with frame counts.

### 4.5 Ship it

`Docs/17` (the packaging order and what each step writes), `Docs/18` (§3 the
12-player smoke run, §4 the budgets, §7 the manual QA pass), `Docs/19` (the Steam
page, the capsule art, the 96-second trailer), `Docs/20` (the release checklists,
top to bottom). `Scripts/Package.bat` and `Scripts/SteamUpload.bat` exist and are
documented; they have never run.

## 5. The conventions this repository enforces

1. **The document is the specification, the script is the implementation, and
   `validate_project.py` is the proof.** A number in a document that the code does
   not have is a build failure, not a note.
2. **Every batch: read the file before editing it, assert the replacement count,
   run the ladder, update `Docs/17` from the checker's own output, commit with a
   message that explains the *why*, and check `git log --oneline -3` before
   committing.** History has vanished four times in this project's sessions; the
   habit of looking is what caught it.
3. **Say what you did not verify.** "Compiles" and "passes" are claims; in this
   repository the second one is checkable and the first one is not, yet.
4. **A comment that explains why is worth three that explain what.** Every unusual
   decision in this codebase has one, and every one of them was written by somebody
   who had just learned it the hard way.
5. **No placeholders.** If a thing cannot be built yet, it is documented in the
   document that owns it, not stubbed in code with a TODO.

## 6. Traps, from this project's own error log

* **The checkers lie about coverage, not about correctness.** A rule that reports
  "nothing found" may have stopped matching. Every checker was verified by
  sabotaging the thing it looks for and confirming it fires — do the same before
  you trust a new one, and sanity-check any `grep` that returns zero.
* **Doc drift is usually the document's fault.** Four movement speeds, a gravity
  scale, an ADS multiplier and a step height were wrong in `Docs/04`; the code was
  right. Reconcile the document to the code, never the reverse.
* **A `UPROPERTY` that shadows an engine property compiles and does nothing.**
  `AirControl` was a fifth of its documented value for weeks because of it.
* **A scoped enum has no relational operators.** `Tier >= EOneBrahamAccessTier::Executive`
  is a compile error that reads like ordinary code. Compare with `==`, or cast.
* **`FString::Split` returns false for a string with no separator**, which is how
  every one-word console command in this project silently did nothing for weeks.
* **A naive reachability scan produces false positives and false negatives.** RPCs
  are called by base name, interface events by `Execute_` or `_Implementation`, and
  delegates bind by address. `report_uncalled.py` knows all four; a fresh grep will
  not.
* **Never hand-write a count into `Docs/17`.** Run `check_doc_numbers.py` and use
  the number it names. Deleting two methods and adding one moved three graded rows.

## 7. Definition of done

The brief, in one paragraph: **ONE BRAHAM** is a vertical multiplayer extraction
shooter inside One Braham, Aldgate — twelve players, three squads of four, no AI,
ground floor to the fifteenth-floor Skydeck. ASCENT (pure PvP extraction), FIRE
DRILL (6v6/8v8 TDM and control) and NIGHT SHIFT (four-player co-op survival,
post-launch). Eight areas, fifteen floors, a lot of glass. Serious gunplay,
believable tired London corporate characters, dry humour through realism only. No
cartoon visuals, no office-supply weapons, no meme characters, no forced jokes, no
American action-movie clichés. UE 5.5, C++ and Blueprint, Enhanced Input, UMG and
CommonUI, GameplayTags, data assets, Chaos, Niagara, Lumen, Nanite, MetaHuman-class
characters, Steam, the Unreal voice module, dedicated and listen servers, Windows
first, £4.99/$5.99, cosmetics only.

Done means: it compiles; the content builds; the map is the fifteen floors the
documents describe; ASCENT can be won and lost, by the winch and by elimination;
FIRE DRILL plays; the HUD, the audio and the settings work; voice chat works;
`Scripts/Package.bat` produces a shipping build; `Docs/20`'s checklists pass;
nothing in §4 is left open and the count in §2's last row is zero — or every
remaining entry has a written reason why it is zero *by design*, in the document
that specifies it.
